Lab 10 · detection engineering

The exploit that injects nothing.

When defenders made memory non-executable (DEP / W^X), injected shellcode stopped running — so attackers stopped injecting. Return- and jump-oriented programming build the payload out of code that's already there: tiny fragments ending in ret or jmp, chained into a program by a crafted stack. There's no sled (Lab 8), no new executable page (Lab 6), no foreign file (Lab 9) — nothing for a byte scanner to see. So the detection moves to the one thing the attack can't fake: control flow that doesn't obey the rules.

Detection only. No gadgets are built or chained here. This lab reasons about the control-flow-integrity signals a defender watches — return provenance, a shadow stack, the stack pivot — and shows how hardware now enforces them.
01 — no payload, only misuse

Reuse leaves a different mark

A normal program returns to the instruction right after a call — that's the contract of a function return. A ROP chain ignores that contract: it returns into the middle of existing functions, to short sequences that do one small thing and ret again, walking down a stack the attacker controls. The bytes are all legitimate, signed, on-disk code. What's illegitimate is the order they run in, and that disorder is measurable.

return provenanceA real return lands on an address immediately preceded by a call. A gadget return lands mid-function, on an address no call ever targets. Check each return's target against that rule.
shadow stackKeep a second, protected copy of every return address as calls happen. On each ret, compare. A ROP chain's returns were never pushed by a real call — so they diverge from the shadow copy. This is now hardware (Intel CET).
the stack pivotTo drive the chain, the exploit first points the stack pointer at attacker-controlled memory — a pivot from the real stack into a heap/buffer region. A stack pointer suddenly outside the thread's stack bounds is a loud, early tell.

03 — who enforces it now

The checks became silicon

Software ROP detection was noisy and slow, so control-flow integrity moved down into the hardware and the loader. You don't hand-roll this in a SOC — you verify it's on, and you alert when a process trips it:

# the enforcement layers, newest first
Intel CET        shadow stack (SS) + indirect-branch tracking (IBT)   ; ret/jmp targets enforced in HW
ARM   PAC / BTI  pointer authentication + branch-target identification ; Apple silicon
MS    CFG / XFG  control-flow guard — valid indirect-call targets only
OS    ACG + stack-pivot checks   ; arbitrary-code-guard, EMET/WDEG heritage

# the SOC job: confirm it's enabled, and treat a CFI fault as an exploit signal
a CET #CP (control-protection) fault  ->  ROP/JOP attempt, not a normal crash
04 — the hard part

JOP doesn't even use ret

  • Jump-oriented programming sidesteps the shadow stack. JOP chains gadgets ending in jmp, driven by a dispatcher, so there's no ret to check against a return-address stack. That's why modern CFI needs indirect-branch tracking (IBT/BTI), not just a shadow stack — defeating one class doesn't defeat the family.
  • Legitimate code breaks the simple rules. Tail-call optimization, longjmp, exception unwinding, and JIT engines all produce returns or jumps that look irregular. Naive provenance checks false-positive on them — which is exactly why the durable version is hardware-assisted and exception-aware.
  • It's an exploitation primitive, not the goal. ROP/JOP usually exists only to flip memory back to executable (e.g. a VirtualProtect chain) and then jump to a conventional payload — which lands you right back in Lab 6's territory. Catch it early (the pivot) or catch the aftermath (the RWX page); best, catch both.
  • You verify posture, then watch for faults. The SOC-practical detection isn't re-deriving CFI in software — it's confirming CET/PAC/CFG are enabled on the fleet and routing control-protection faults into the timeline (Lab 7) as exploitation evidence.
