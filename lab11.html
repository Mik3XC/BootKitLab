Lab 11 · detection engineering · home turf

Persistence, on your own Mac.

Lab 1 was persistence in the boot chain. This is the version that actually runs on the machine in front of you. An implant that survives a reboot has to register somewhere the OS will read on the way up or on login — and macOS has a fixed, well-known set of those places. That's the defender's advantage: the hiding spots are enumerable. You list them, check each item's signature and path against what belongs, and diff against a baseline. New, unsigned, and in the wrong place is the whole game.

Analysis only. This reads the persistence locations and classifies what's there. It installs nothing, loads no agent, and changes no plist — it's the sweep, not the implant.
01 — the hiding spots

Where it has to live

To survive, persistence registers with one of a handful of OS mechanisms. Each is a place you can enumerate:

LaunchAgents / LaunchDaemonsThe big one. plists in ~/Library/LaunchAgents (per-user), /Library/LaunchAgents + /Library/LaunchDaemons (system), run by launchd with RunAtLoad / KeepAlive. Most macOS malware lands here.
Login items / BTMModern background items register via SMAppService and are tracked in the Background Task Management database (macOS 13+). sfltool dumpbtm lists them; a new ad-hoc-signed helper here is a classic dropper tail.
login / logout hooksLegacy com.apple.loginwindow LoginHook running a shell script. Deprecated, still works, and rarely legitimate today — a strong signal when present.
cron / periodic / atClassic Unix scheduling still runs. A crontab entry or a script dropped into /etc/periodic is low-tech persistence that EDR sometimes overlooks.
config profiles / MDMA .mobileconfig can install payloads and settings with authority. An unexpected profile (profiles list) is persistence and policy control at once.
dylib insertionDYLD_INSERT_LIBRARIES in a plist's environment, or a hijackable @rpath, loads attacker code into a legit process on launch — ties straight to Lab 6 & 9.
02 — run the sweep

List, then judge

A snapshot of the persistence locations on a sample Mac. Run the sweep — each item is judged by who signed it (Apple / valid Developer ID / unsigned-or-ad-hoc), where its program lives (a system path vs. /tmp or a hidden dir), and whether it masquerades as something Apple. Apple system agents and known vendors pass; the odd ones out light up.

03 — how you'd really watch it

Enumerate, baseline, diff

The sweep above is a point-in-time list. The real detection is continuous: enumerate the locations, establish a baseline of what's normal for this host, and alert on anything that appears — the same baseline-then-diff from Labs 1 and 3, pointed at launchd.

# osquery — the persistence locations as tables, queryable and diffable
SELECT name,path,program,run_at_load FROM launchd
  WHERE run_at_load=1;                      # agents/daemons
SELECT * FROM startup_items;   SELECT * FROM crontab;
SELECT * FROM launchd_overrides;  # disabled→enabled flips

# eslogger — watch the locations change in real time (Endpoint Security)
eslogger btm_launch_item_add create       # new login item / plist write

# signing & profiles
codesign -dv --verbose=4 <program>   ·   spctl --assess   ·   profiles list

# reference tools (Objective-See)
KnockKnock  # enumerate every persistence point, check signatures
BlockBlock  # alert the moment something persists

A new item becomes a Vertical case (Lab 7): the plist, its signature verdict, the writing process and its lineage, captured as evidence.

04 — the hard part

Legit Macs are noisy

  • There are a lot of real agents. A working Mac has dozens of legitimate LaunchAgents — updaters (Google, Microsoft, Adobe), sync clients, drivers. The flag is never “has a LaunchAgent,” it's new + unsigned + wrong-path + unexpected, together.
  • Signed and notarized isn't innocent. Developer ID gets stolen and abused, and legitimately-signed installers drop helpers. Signature tells you who and whether revoked — a necessary check, not a verdict (same lesson as Lab 9).
  • SIP hides the system from you — and that's good. System-protected locations can't be tampered with or freely read; you lean on the Endpoint Security framework and signed system snapshots rather than scraping protected paths. Detection works with the platform's integrity, not around it.
  • Permissions ≠ persistence, but they travel together. TCC (privacy permissions) and persistence are different things, yet an implant usually wants both — so an unexpected new agent that has also been granted Full Disk Access or Accessibility is a louder, corroborated signal than either alone.
